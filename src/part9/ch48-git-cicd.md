# 第 48 章 Git 工作流、CI/CD 与代码审查

> 这一章讲团队协作的基本功——怎么管理代码版本、怎么多人协作不打架、怎么自动化地把代码安全送上线。这些最容易被轻视，却最能在面试和试用期暴露真实水平。本章从"第一个 Git 仓库"讲起，到大厂团队的真实工程实践。

## 48.1 Git 是什么：代码的"存档与平行宇宙"

写代码就像打游戏：你需要**随时存档**（万一改坏了能读档）、需要**开平行宇宙**（试验新玩法不影响主线）、还要能和队友**合并各自的进度**。Git 就是干这个的"版本控制系统"。

先把日常流程跑通：

```bash
# 第一次用先设置身份
git config --global user.name "你的名字"
git config --global user.email "you@example.com"

mkdir demo && cd demo
git init                          # 把当前文件夹变成一个 Git 仓库
echo "# Demo" > README.md
git status                        # 不知道现在啥情况？先 status，这是你最好的朋友
git add README.md                 # "暂存"：把改动放上准备区
git commit -m "feat: 添加 readme"  # "提交"：存一个档（一张不可变的快照）
git log --oneline                 # 看历史存档
```

理解这个"三区模型"就懂了 Git 的核心：

```
你正在改的文件  --git add-->  暂存区（准备提交的）  --git commit-->  历史（一串存档）
```

**分支**就是"平行宇宙"——开个新分支做新功能，不影响主线：

```bash
git switch -c feat/login    # 创建并切到新分支（一个平行宇宙）
# ……在这改代码、提交……
git switch main             # 切回主线
git merge feat/login        # 把平行宇宙的成果合并回主线
```

**和远程协作**（GitHub）：

```bash
git clone 仓库地址      # 把别人的仓库整个抄一份到本地
git pull               # 拉取队友的新提交
git push               # 把自己的提交推上去
# 然后在 GitHub 上开一个 Pull Request（PR）：请求把你的分支合进主线，触发审查和自动检查
```

如果两个人改了同一行，合并时会**冲突**——Git 不替你决定，会在文件里标出来：

```
<<<<<<< 你的版本
=======
对方的版本
>>>>>>>
```

你手动编辑成正确的内容、删掉这些标记，再 `git add` + `git commit` 即可。冲突不是事故，是协作日常；分支活得越短、PR 越小，冲突越少。

最后，新仓库第一件事是写 `.gitignore`，告诉 Git 哪些不要管（构建产物、依赖、密钥）：

```
target/
node_modules/
.env*
```

## 48.2 几个进阶但常用的命令

```bash
git rebase -i main       # 整理提交历史（合并零碎提交、改提交信息）
git cherry-pick abc123   # 把某一个提交单独"摘"过来（紧急修复回灌常用）
git bisect               # 二分查找：自动定位"哪次提交引入了 bug"——排查神器
git reflog               # 后悔药：找回你以为弄丢的提交
```

`git bisect` 特别值得一提：当你发现"评测通过率不知道哪天开始掉了"，它能在几十个提交里二分定位到罪魁祸首，配合一个判断好坏的脚本还能全自动跑。

## 48.3 工作流：主干开发 + 短命分支

现在团队的共识是**主干开发**——分支活不过一两天就合并，而不是开一个分支做一个月。

```
main ──●──●──●──●──   主线随时可发布，每次合并都过完整的自动检查
        \   /
  feat ──●─●          短命分支：1-2 天，小 PR（最好 < 400 行）
```

配套几条纪律：**提交信息规范**（用 `feat:`/`fix:` 这种前缀）；**PR 要小**（超过 400 行审查质量就断崖下跌）；**没做完的功能用开关藏起来**，而不是留个长命分支（长命分支 = 合并地狱）。

## 48.4 CI：自动化质量门禁

**CI（持续集成）解决什么问题**？没有 CI 时，"代码能不能编译、测试过没过"全靠人自觉，迟早有人忘了、把坏代码合进主线。CI 就是**每次提 PR 自动跑一遍检查**，不过就不让合并。

检查内容就是每个语言的"四件套"：格式化、lint（查代码问题）、类型检查、测试。用 GitHub Actions 写（放在 `.github/workflows/ci.yml`），这是 Rust 部分的样子：

```yaml
name: CI
on: [pull_request]           # 每次提 PR 就触发

jobs:
  rust:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cargo fmt --check                          # 格式
      - run: cargo clippy --all-targets -- -D warnings  # lint（有警告就失败）
      - run: cargo test --all-features                  # 测试
```

前端、Python 的 job 同理（`pnpm tsc + eslint + vitest`、`ruff + pyright + pytest`）。两个实用原则：**用缓存 + 只跑改动的部分**，让 PR 在 5 分钟内出结果（反馈太慢就没人等、坏代码也合了）；**构建 Docker 镜像只在合并到 main 后做**，按提交号打 tag。

## 48.5 CD：自动化部署上线

**CD（持续部署）**接着 CI，把"绿色的主线"自动送上生产。现代做法是 **GitOps**——把"线上该跑什么版本"也写进一个 git 仓库，工具（Argo CD）自动让线上向它看齐：

```
合并到 main → CI 通过 → 构建镜像 → 更新 GitOps 仓库里的镜像版本
            → Argo CD 自动同步到测试环境 → 冒烟测试 → 金丝雀 5%→100% → 生产
```

三个好处：**升级**就是改 GitOps 仓库里的一行（人不碰 kubectl）；**回滚**就是 `git revert` 那次提交，一分钟生效；全程**有记录可审计**。

Agent 平台还有个特别的上线门禁：**把第 47 章的"金丝雀任务集"跑在测试环境**，如果 Agent 的通过率/行为漂移超标就**阻止上线**。把"模型行为回归"纳入部署门禁，是 Agent 团队区别于普通后端团队的标志。

## 48.6 代码审查：怎么给、怎么收

**作为 PR 作者**，让别人容易审你的代码：标题讲清"为什么改"、描述带上怎么测/截图；自己先从头读一遍 diff，别留调试残留；PR 尽量小。

**作为审查者**，分层把关，别一上来只挑格式问题：

| 优先级 | 看什么 |
|---|---|
| 正确性 | 边界情况、并发、错误处理对不对 |
| 设计 | 接口契约、是否向后兼容 |
| 安全 | 有没有注入、越权、密钥泄露 |
| 可维护 | 命名、测试够不够（这类小意见标 nit:，不阻塞合并）|

文化上：**对事不对人**（说"这个函数会……"而不是"你怎么……"）；来回超过三轮就直接拉个会聊。

**AI 时代新增一条**：AI 生成的代码，**作者本人负全责**——提交前必须逐行读懂，不能"AI 写的我没看"。CI 里可以加 AI 自动审查作为补充，但替代不了人。

## 48.7 用工具兜底，别靠自觉

规范靠自觉必然失守，要靠工具强制：

- **pre-commit**：本地提交前自动跑格式化、密钥扫描（gitleaks），秒级拦住低级错误。
- **分支保护**（在 GitHub 设置）：main 禁止直接 push；PR 必须 CI 通过 + 至少 1 人批准才能合；用 CODEOWNERS 指定每个模块的负责人自动成为审查者。

```
# CODEOWNERS 文件示例
/server/   @team-harness
/web/      @frontend-guild
/deploy/   @sre
```

## 48.8 小结与练习

- Git 是代码的存档（commit）+ 平行宇宙（branch）+ 合并协作；三区模型：工作区→暂存区→历史；冲突手动解、分支要短命。
- 主干开发 + 小 PR + 规范提交信息。
- CI 每次 PR 自动跑"格式/lint/类型/测试"四件套，5 分钟内反馈；CD 用 GitOps 自动上线、git revert 即回滚，并把模型行为回归纳入门禁。
- 代码审查分层把关（正确性 > 设计 > 安全 > nit）；AI 写的代码作者负全责；规范靠工具兜底。

**练习**

1. 给你的 rust_agents 仓库配齐：pre-commit、分支保护、一个能跑 `cargo test` 的 CI。
2. 故意埋一个 bug 再用 `git bisect` 自动定位它（写一个判断好坏的 test.sh）。
3. 完整走一遍 PR 流程：开 issue → 短命分支 → 小改动 → 自审 → 提 PR 等 CI → 合并。
