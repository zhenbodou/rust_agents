# 第 47 章 Agent 容器服务：安全、快速、可复现的沙箱

> 这一章讲一个听起来像"运维杂活"、实则是 RL 训练和评测**地基**的东西——Agent 容器服务。它给每个 Agent 提供一个干净的执行环境（沙箱）。它不稳，楼上全塌。本章讲清这个服务长什么样、为什么难、怎么维护。前面 Docker/K8s 的知识在这里全用上。

## 47.1 它是什么、难在哪

一句话：**给每个 Agent 任务提供一个干净、隔离、可复现的执行环境的服务**。Claude Code 的沙箱、RL rollout 的环境、评测平台跑 Agent 的地方，都是它。

为什么难？因为它要同时满足一堆互相拉扯的需求：

| 需求 | 为什么要 | 不满足的后果 |
|---|---|---|
| 隔离 | Agent 跑的是模型生成的代码，不可信 | 一个任务污染另一个，或攻破宿主机 |
| 快速供给 | 训练要几百个并发 | 起得慢，GPU 干等环境，烧钱 |
| 可复现 | 同样输入要同样行为 | 训练曲线没法 debug |
| 资源限制 | 防失控 | 一个 fork 炸弹拖垮整台机器 |
| 网络管控 | 防数据外泄 | prompt injection 把数据传出去 |

## 47.2 隔离要多强：选对"沙箱"

核心判断：**Agent 执行的是模型生成的任意代码，等同于"运行不可信代码"**。所以隔离强度很关键。几种选择：

| 技术 | 隔离强度 | 启动速度 | 适用 |
|---|---|---|---|
| 普通 Docker 容器 | 中（共享内核） | ~500ms | 内部可信负载、评测 |
| **gVisor** | 高（拦截系统调用） | ~700ms | 跑不可信代码的默认选择 |
| **Firecracker 微虚拟机** | 很高（独立内核） | ~125ms | 对外产品、多租户 |

为什么普通 Docker 不够？回忆第 45 章——容器共享宿主内核，内核有漏洞就可能"逃逸"。所以跑不可信代码时，要么用 gVisor（在中间加一层拦截，让容器碰不到真内核），要么用 Firecracker（干脆给每个沙箱配独立的迷你内核）。

无论用哪种，容器安全基线都要拉满（K8s 配置片段）：

```yaml
securityContext:
  runAsNonRoot: true                  # 不用 root 跑
  allowPrivilegeEscalation: false     # 不许提权
  readOnlyRootFilesystem: true        # 根目录只读，只有工作区可写
  capabilities: { drop: ["ALL"] }     # 去掉所有特权能力
resources:
  limits: { cpu: "2", memory: 4Gi }   # 硬限制
```

再加上"限制进程数"（防 fork 炸弹）和"默认禁止联网、只放行必要地址"（防数据外泄）。

## 47.3 沙箱池：让供给从"秒"变"毫秒"

每个任务都现起一个容器太慢（要几秒）。生产做法是**池化**——预先准备一批热好的沙箱待命，要用直接取，用完**重置**再放回去，而不是销毁重建：

```rust
pub struct SandboxPool {
    warm: ArrayQueue<SandboxHandle>,   // 一批预热好的空闲沙箱
    target_warm: usize,                // 水位线，后台自动补充
}

impl SandboxPool {
    // 取一个用
    pub async fn acquire(&self) -> Result<LeasedSandbox> {
        match self.warm.pop() {
            Some(sb) => Ok(LeasedSandbox::new(sb)),
            None => self.cold_start().await,   // 池空了才现起一个（并报警）
        }
    }

    // 用完归还：重置而不是销毁
    pub async fn release(&self, sb: LeasedSandbox) -> Result<()> {
        match timeout(Duration::from_secs(5), sb.reset()).await {
            Ok(Ok(())) => { self.warm.push(sb.into_inner()).ok(); Ok(()) }
            _ => sb.destroy().await,    // 重置失败/超时 → 直接销毁，绝不复用脏环境
        }
    }
}
```

重置怎么这么快（约 50 毫秒）？靠第 45 章讲的"联合文件系统"——镜像层是只读共享的，每个沙箱只有一个可写上层，重置就是"丢掉那个上层、回到初始状态"。

**一条铁律**：重置失败一律销毁。**脏环境比慢更可怕**——一个没清干净的环境会污染下一个任务，让数据不可信。

## 47.4 环境镜像：分层设计

不同任务需要不同环境（修 Python 仓库 vs 修 Rust 仓库）。镜像按"变化频率"分三层，最大化复用和缓存（呼应第 45 章的分层思想）：

```dockerfile
# L1 基础层：所有环境共享（操作系统 + 通用工具），几乎不变
FROM ubuntu:24.04 AS agent-base
RUN apt-get install -y git curl ripgrep build-essential

# L2 运行时层：按语言分（Python 生态、Node 生态…），偶尔变
FROM agent-base AS agent-python
RUN curl -LsSf https://astral.sh/uv/install.sh | sh

# L3 任务层：具体仓库 + 它的依赖，每个任务集一个
FROM agent-python AS task-django
RUN git clone --depth 1 https://github.com/django/django /workspace
```

**两条可复现性铁律**：镜像引用一律用 digest（`镜像@sha256:...`）不用 tag——tag 会被改，digest 永远指向同一份；每个镜像内置一个"指纹文件"（构建时间、git 版本、依赖哈希），这就是第 43 章说的"环境指纹"的来源。

## 47.5 依赖管理：两条线分开治

这是 JD 里"框架版本同步、依赖管理"的真实痛点。要管两条线：

**平台自己依赖的框架**（你代码 import 的 LangChain、vLLM 等，每周都发新版）：用自动化工具（Renovate）定期开升级 PR；每个框架的适配器配"契约测试"，升级后跑一遍，上游一改坏就立刻发现；锁文件进 git，CI 用"冻结模式"安装保证一致。

**沙箱内 Agent 装的包**（Agent 自己 `pip install` 的）：只允许走内部的"包缓存代理"——既加速、又能在断外网时仍可用、还能审计和禁用危险版本；用一份全局"版本约束"文件钉住关键包，防止 Agent 装个不兼容版本导致环境漂移。

## 47.6 把它当正经线上服务来运维

这个服务就是个线上服务，要用 SRE 的方式管（第 48a 章会深入 SRE）。定义清楚"好"的标准（SLO）：

| 指标 | 目标 |
|---|---|
| 沙箱供给延迟 P99 | < 500 毫秒（池命中）|
| 非任务原因的异常中断率 | < 0.1% |
| 环境漂移（金丝雀任务集分数波动）| < 2% |

几个关键运维动作：

- **告警**：沙箱池快空了、重置失败率升高、环境漂移超标，都要自动报警。
- **僵尸回收**：任务结束但容器没被回收（网关崩了等原因）会慢慢吃光集群。给每个沙箱设一个"超时自动回收"，再用一个定时任务对账"应该有的 vs 实际在跑的"，把孤儿杀掉。
- **变更走金丝雀**：升级环境镜像 = 改变了训练环境，必须先用固定的"金丝雀任务集"跑一遍，分数漂移超标就自动回滚。**"先跑金丝雀再全量"这句话，面试里能值一个级别。**

## 47.7 小结与练习

- Agent 容器服务 = 跑不可信代码的平台：gVisor / Firecracker 起步，普通 Docker 必须加足安全限制 + 默认断网。
- 供给速度靠"沙箱池 + 重置复用"（重置失败一律销毁，脏环境最可怕）。
- 可复现靠 digest 引用 + 环境指纹 + 金丝雀任务集。
- 依赖治理分两条线：平台框架（自动升级 + 契约测试）、沙箱内包（缓存代理 + 版本约束）。
- 它是个 SRE 视角的活：SLO、告警、僵尸回收、金丝雀变更。

**练习**

1. 用 Docker API 写一个最小沙箱池：维持 4 个预热容器，实现"取/还/重置"，测一下供给延迟。
2. 给 mini-claude-code 的 bash 工具加上资源限制（1 核 CPU、512MB 内存、最多 64 个进程），用 fork 炸弹验证防线有效。
3. 写一份"环境镜像升级操作手册"：金丝雀任务集怎么选、分数漂移阈值定多少、怎么回滚。
