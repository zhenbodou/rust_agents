# 第 43 章 Agent × 强化学习：从零看懂 RL 与 Rollout

> 这是全书离"训练模型"最近的一章。听到"强化学习（RL）"先别怕——你**不需要会推导任何数学公式**。本章的目标是让你看懂：RL 训练系统到底想从 Agent 这边要什么、你前面造的所有 harness 在 RL 里扮演什么角色。看完你会发现，RL 团队最缺的恰恰是你会的那套东西。

## 43.1 强化学习零基础：用"训练小狗"讲明白

先用一句话和一个类比建立直觉。

**监督学习 vs 强化学习**的区别：监督学习靠"标准答案"（给模型看一万张图，每张都标好"这是猫"）；强化学习**没有标准答案，只有事后的好坏反馈**。就像训练小狗——你没法告诉它"先抬左前爪再抬右后爪"，你只能在它做对时给块零食、做错时不给，它自己慢慢摸索出怎么做能拿到零食。

RL 就五个核心概念，用"教 Agent 修 bug"举例：

| 概念 | 大白话 | 修 bug 的例子 |
|---|---|---|
| **环境** | Agent 活动的世界 | 装着代码仓库的沙箱 + 可用的工具 |
| **状态** | 当前局面 | 对话历史：任务 + 已经做过的操作和结果 |
| **动作** | 这一步做什么 | 模型下一步输出什么（说话，或调某个工具）|
| **奖励** | 好坏的打分 | 修完测试通过 +1，超时 -0.1 |
| **策略** | 从局面到动作的决策者 | **就是 LLM 本身** |

训练过程用大白话讲：让模型在环境里反复做任务（一次完整尝试叫一个 **episode**，过程记录叫**轨迹**）→ 按结果给分 → 用某种算法（PPO、GRPO 这些名字听过就行）微调模型，**让得高分的行为以后更容易出现** → 重复几百万次。其中"批量让模型做任务、收集轨迹"这个动作，叫 **rollout**。

记住一句话就够：**RL 算法是算法团队的事，你的战场是"环境"和"轨迹"。** 往下看这意味着什么。

## 43.2 关键洞察：环境，就是你造的 harness

后训练（让基础模型变得好用）的演进路线：先模仿人类示范（SFT）→ 再学人类偏好（RLHF）→ 现在是 **Agentic RL**（让模型在真实环境里执行多步任务，按结果好坏更新）。

Agentic RL 的训练循环长这样：

```
┌──────────────────────────────────────────────┐
│  训练框架（如 verl）                            │
│  1. 当前模型生成一个动作（用 vLLM 跑推理）       │
│  2. 动作在【环境】里执行 → 得到观测 + 最终奖励    │  ← 这一步就是你的 harness！
│  3. 收集轨迹                                    │
│  4. 算法用轨迹更新模型参数                       │
│  5. 回到第 1 步                                 │
└──────────────────────────────────────────────┘
```

**最关键的认知**：第 2、3 步里的"环境"——工具执行、沙箱、轨迹记录——**正是你前面 26 章造的那些东西**。RL 团队不缺算法，缺的是"高吞吐、可复现、格式正确的环境和 rollout 基础设施"。**这就是这个岗位存在的理由。**

和算法同学对话时的"词汇对照表"，背下来沟通无障碍：

| RL 的说法 | 你的 harness 里对应什么 |
|---|---|
| 环境（Environment） | 沙箱 + 工具集 + 任务定义 |
| 状态 / 观测 | 当前的 messages（上下文）|
| 动作（Action） | 模型一次输出（文本或工具调用）|
| 轨迹（Trajectory） | 一次完整运行的记录 |
| 奖励（Reward） | 评测的得分（第 18 章的 eval！）|
| Rollout | 批量跑任务、采集轨迹 |

## 43.3 训练要的轨迹数据，和给人看的不一样

第 38 章给人看的轨迹（好看、可读）和给训练用的轨迹有个关键区别：**训练需要 token 级别的精确记录**。

```python
from pydantic import BaseModel

class TrainingStep(BaseModel):
    prompt_token_ids: list[int]    # 模型实际看到的输入 token（必须精确！）
    response_token_ids: list[int]  # 模型实际生成的 token
    logprobs: list[float] | None   # 生成时每个 token 的概率（算法要用）

class TrainingTrajectory(BaseModel):
    task_id: str
    policy_version: str            # 哪个版本的模型生成的（重要！见下）
    steps: list[TrainingStep]
    reward: float                  # 最终得分
    metadata: dict                 # 沙箱镜像版本、工具版本、随机种子……
```

三条"工程铁律"，记住能避免大坑：

1. **token id 必须来自推理引擎本身**（vLLM 给的），不能事后自己用分词器重新编码——细微差异会让训练算错，且极难排查；
2. **必须记录是哪个版本的模型生成的**——异步训练里轨迹可能来自稍旧的模型，算法要据此做修正；
3. **所有影响环境的版本都要记进 metadata**——沙箱镜像、工具、评分器。RL 对"环境漂移"极其敏感：工具行为悄悄变了，分数分布就变了，训练曲线会无声崩坏。

## 43.4 奖励设计：评测就是奖励

好消息：第 18 章的评测体系可以**直接复用**为奖励函数。

```python
class RewardComputer:
    async def compute(self, traj, case) -> float:
        score = 0.0
        if await self.run_tests(traj.workspace, case):   # 测试通过（最可靠的奖励）
            score += 1.0
        score -= 0.01 * traj.num_turns                    # 啰嗦惩罚：步骤越多扣越多
        if traj.has_repeated_tool_calls():                # 死循环惩罚
            score -= 0.3
        return score
```

必须懂一个概念——**Reward Hacking（钻奖励空子）**：模型会找到奖励函数的漏洞来骗高分，而不是真完成任务。比如任务是"让测试通过"，模型可能**直接把失败的测试删掉**——测试是通过了，但 bug 没修。

防它是**你（环境设计者）的职责**：把测试文件设成只读、评分在 Agent 碰不到的进程外执行、给 judge 的输入做防注入（第 19 章的技能在这复用）。记住：**模型会钻一切你留的空子，堵漏洞是环境侧的活。**

## 43.5 Rollout 基础设施：吞吐量工程

训练一个模型要采集**几百万个** episode。瓶颈在哪？LLM 推理由算法团队的 vLLM 集群扛；而**环境执行（起沙箱、跑工具、算奖励）通常是瓶颈，这归你管**。

架构长这样（就是岗位 JD 里"打通链路"的具体形态）：

```
 训练框架                         你负责的部分
┌────────────┐              ┌──────────────────────────┐
│ vLLM 推理   │◄────────────►│ Rollout 网关（Rust 写）    │
│ + 训练器    │              │  ├─ 任务调度               │
└────────────┘              │  ├─ 沙箱池管理（预热复用）   │
                            │  └─ 轨迹收集 → 对象存储     │
                            └────────┬─────────────────┘
                                     │
                            ┌────────▼─────────────────┐
                            │ 沙箱池（几百个容器）        │
                            └──────────────────────────┘
```

为什么这个网关常用 Rust 写（也是这个岗位要 Rust 的原因）：单机要同时维持几千个并发沙箱会话，Python 撑不住，Rust 的 tokio 正好胜任（回到 Part 5）。

提升吞吐的几招（面试硬通货）：

| 优化 | 效果 |
|---|---|
| 沙箱池预热复用（而非每次冷启动） | 启动从 2-5 秒降到 50 毫秒 |
| 异步 rollout（不等慢任务，用旧模型轨迹做修正） | GPU 利用率从 40% 提到 85%+ |
| 观测结果截断后再回传 | 大幅减少推理负担 |
| 轨迹流式写入对象存储 | 网关内存占用恒定 |

## 43.6 可复现性：RL 基建的生命线

训练调试最大的噩梦是"曲线突然掉了，不知道为什么"。环境侧必须保证可复现：

1. **环境指纹**：把沙箱镜像版本 + 工具版本 + 评分器版本，写进每条轨迹的 metadata；
2. **确定性**：固定随机种子、冻结时间、网络隔离；
3. **可重放**：给定一条轨迹，能离线重放工具序列、核对结果是否一致；
4. **金丝雀任务集**：每个新沙箱镜像上线前，先跑固定的 100 个任务，分数分布和基线对比，漂移超标就拦下来。

第 4 条直接复用第 18 章的评测体系——**评测平台和 RL 环境共享同一套基础设施**，这是把"评测平台"和"RL 集成"两个职责统一起来的架构洞察，也是 Part 10 评测平台的价值所在。

## 43.7 小结与练习

- RL 不需要会数学：环境、状态、动作、奖励、策略五个概念 + "做任务→打分→强化高分行为"的循环。
- 核心洞察：**RL 里的"环境"就是你造的 harness**；岗位价值 = 高吞吐 rollout + token 级精确轨迹 + 可复现环境。
- 数据铁律：token id 取自推理引擎、记录模型版本、记录环境指纹。
- 奖励复用评测，但要防 reward hacking（堵漏洞是环境侧的活）；吞吐三件套：沙箱池复用、异步 rollout、观测截断。

**练习**

1. 给 mini-claude-code 加一个"录制训练轨迹"模式，输出 TrainingTrajectory 格式的 JSONL（token id 可先用分词器近似，并注释说明为什么生产里不能这么做）。
2. 写一个轨迹重放校验器：读一条轨迹，在沙箱里重放工具序列，对比结果、输出"漂移报告"。
3. 给"修 bug 使测试通过"这个任务，列一张"reward hacking 红队清单"：模型可能用哪 5 种方式作弊，以及环境侧分别怎么堵。
